# Контракт пакета Тильды и Яндекс Облака — проход 65

Пакет готовится только из release-сборки, `scripts/prepare-tilda-release.py` не публикует его. Адресат ограничен СОЮЗом: Тильда46815509, soyuz.hair, bucket shaver, префикс Soyuz/releases/. Конфигурация содержит11контентных страниц; шапка/подвал выделяются в2общие native-страницы. Факт readback/publish хранится отдельно в deploy/tilda-pages.json и обновляется после переноса, а не при локальном prepare.

Встроенный и внешний CSS проходят одну protected_css, без изменения взаимной специфичности. Публичные ссылки сохраняют query иfragment. Обход графа включает зависимости из HTML, текстовых ресурсов и относительных ссылок.

## Относительные изображения новостей

Fallback data/news.json по контракту использует ../media/news/*.webp. Эти файлы не переводятся в независимый SHA-префикс: они лежат под тем же build-префиксом, что и JSON. Поэтому native new URL(variant.url, feedURL) совпадает с фактическим URL файла в manifest. Остальные бинарные изображения, видео, аудио и шрифты сохраняют SHA-стабильные URL assets/<sha20>/... при изменении только кода. JSON-формат и runtime validator новостей не расширены.

## Воспроизводимое сжатие и immutable

gzip.compress(mtime=0) в Python3.12 делегирует создание заголовка платформенному zlib: Windows иUbuntu дают различные OS bytes при одинаковом исходном содержимом. Это вызывало бы одинаковыйbuild/URL с разными wire-хешами и отказ ImmutableConflict при переносе между CI иWindows.

Используется GzipFile(filename='',mtime=0) через BytesIO: нет имени файла и даты, OSbyte255. Параметры codec явно помещены в manifest: format,level,mtime,os,zlibVersion. Канонический JSON этих параметров участвует в build digest. Одинаковые исходные/нормализованные ресурсы и codec дают один build; новая версия zlib получает новый build-префикс. ОС, дата и случайные значения в build не входят. Поколение экспортного алгоритма поднято доv4, чтобы новый способ адресации не переиспользовал старые immutableURL.

Загрузчик проверяет точный wire SHA и HTTP metadata и останавливается при существующем ключе с другими байтами. Bootstrap проверяет транспортный, декодированный и исходный хеши и не перезаписывает локальные отличающиеся исходники.

## Канонические MIME и неизменяемые бинарные URL

Прямое чтение Cloud показало ошибку Windows-реестра mimetypes: WOFF2, TTF и WebP получали application/octet-stream. Разрешение CORS для soyuz.hair, www и технического домена при этом работало. Значения MIME теперь принадлежат явной CONTENT_TYPES: image/webp, font/woff2, font/woff, font/ttf и остальные типы активного графа не зависят от ОС. Типы шрифтов соответствуют [RFC8081](https://www.rfc-editor.org/rfc/rfc8081.html).

Текущий digestv4 включает MIME. Для бинарного ресурса идентификатор учитывает MIME, нулевой разделитель и исходные байты; для новостей по-прежнему сохраняется общий относительный build-префикс с JSON. Это создаёт новые URL правильного представления вместо перезаписи заголовков старых immutable-объектов. При следующих изменениях только кода неизменённые бинарные ресурсы продолжают использовать те же URL. Оригинальные файлы и старые объекты не удаляются.

Отдельный regression подменяет OS MIME detector и проверяет неизменность канонических типов, новый идентификатор представления и стабильность URL между кодовыми сборками. Полный package-gate теперь сравнивает contentType каждого объекта с этим же владельцем. Промежуточный cc3-пакет используется только как проверенный входной public graph для чистой сборки; финальная production-сборка готовит собственный пакетv4.
